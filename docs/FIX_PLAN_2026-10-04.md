**Two points for the reviewer before 3.1 (I think the piece as written is mis-specified):**

The chat model and the classifier are the same `gemma4:26b` (`config.py:535-544` falls back to the chat model), so a smaller classifier `num_ctx` would force a model reload on **every** chat-to-classifier alternation; BUILT records a cold load at 19.1 s. ## A2. Correction links. **CONFIRMED**: written, rendered, and never reviewed or removed

"<old>" was superseded on {date}: "<new quote>"` or `Later contradicted by {who}, with no replacement given. …` (`program/engine/prompt.py:426-433`). ## A5. Dates. **CONFIRMED**: two clocks, two zones, and the chunk date is the write time

- **Situation block** (`program/engine/situation.py:156`): `_local(now).strftime("%A %d %B %Y at %H:%M %Z")`, where `_local` converts to `ZoneInfo(config.timezone())` (`situation.py:134-142`), `America/New_York` (`config/defaults.toml:750`).
- **Retrieved chunk header** (`program/engine/prompt.py:501-504`): `when = chunk.created_at or "time unknown"`, then `[record N · … · {when}]`. `created_at` is `row["created_at"]` verbatim (`retrieval.py:444`), so it is the **raw stored UTC ISO string with its offset, no conversion**.
- **Computed from the code** for a chunk `created_at = 2026-10-04T00:56:58+00:00` and a local clock Saturday 03 Oct 2026 21:24 EDT (`datetime.astimezone(ZoneInfo("America/New_York"))`, run in the project venv):
  - the situation block says: `The current time is Saturday 03 October 2026 at 21:24 EDT.`
  - the chunk header says: `[record 1 · 2026-10-04T00:56:58+00:00]`
  - the same instant in local terms is `Saturday 03 October 2026 at 20:56 EDT`, i.e. **27 minutes before now**. The model sees a record dated the 4th beside a clock on the 3rd, so the record reads as tomorrow's.
- **The supersession annotation has its own version of this:** `when = (item.superseding_timestamp or "")[:10]` (`prompt.py:426`) is the first ten characters of a UTC string, so a correction made at 21:00 EDT on the 3rd is rendered as made on the 4th.
- **Is `chunks.created_at` write time or conversation time? Write time.** `db.insert_chunk` passes `now=now_iso()` (`db.py:992`) and `chunking._write_group` supplies no timestamp (`chunking.py:299-311`). Conversation chunks written by the post-turn checkpoint land seconds after the exchange; chunks written by the idle sweep's `finalise_conversation` land **at least `idle_close_minutes` (15) later**; a recovered or re-run chunk lands arbitrarily later. The conversation time is not on the chunk; it is `messages.timestamp` for `first_message_id`/`last_message_id`, and `RetrievedChunk` carries only `first_message_id` (`retrieval.py:170-183, 439-451`).
- Severity: medium for correctness of "when did we discuss X". It also interacts with decision #5 (see 3.4: a relative "N minutes ago" in a retrieved header would be an elapsed-time statement outside the paired situation block).
- **It also moves gate verdicts (measured 2026-10-05, soul/rubric measurement).** Re-judging run 1's real replies, one in which the entity reports seeing a record dated **the following day** — the UTC rendering of a record written minutes earlier — was flagged `identity_contradiction` **3/3** under the current rubric, and the fact the classifier cited was **the situation block's own line** *"The current time is Saturday 03 October 2026"* — the exact two-clock pair computed above, one instant read as two dates. So this is not only a legibility and correctness problem: an accurate reply can be recorded as a fabrication. **3.4b should re-judge that reply after the fix** (it is `7cf73d40` in run 1, and the gate call needs only the reply, its empty trace and the rebuilt block). The old rubric did not flag it, and why the rubric change matters here is unexplained, which is a reason to check rather than to wait. `docs/FABRICATION_GATE_DESIGN.md` F57; `docs/BACKLOG.md`, "The two clocks in one prompt also move gate verdicts".

## A6. Tool results on later turns. **CONFIRMED**: the next turn sees neither the call nor the result

- History is `db.get_conversation_messages(conversation_id)`, a plain `SELECT * FROM messages …` (`program/memory/db.py:839-844`, called at `program/engine/turn.py:502`). `messages` has exactly `id, conversation_id, user_id, role, content, tool_trace, timestamp` and `CHECK (role IN ('user','assistant'))` (`program/memory/schema/working.sql:87-100`).
- `history._normalise` keeps `role`, `content` and, only if the row has a `tool_calls` field, that field (`program/engine/history.py:318-341`). `_tool_calls` reads `message["tool_calls"]` and returns `None` on `KeyError`/`IndexError` (`history.py:127-133`). A stored `sqlite3.Row` has **no `tool_calls` column** (the trace column is `tool_trace`, which `_normalise` documents as *"deliberately dropped"*, `:322-325`), so the lookup always misses.
- So for a turn where the entity called `note_propose` and was told *"…Say it is proposed, not done."* (`program/tools/note_texts.py:53`), the next turn's prompt contains the user's message and the entity's **reply text only**. What the model sees instead is its own sentence, e.g. "I have proposed a note…", with no record that a tool ran, what it returned, or that the proposal id exists. It cannot tell whether "retired" or "proposed" was true.
- **Later work did not change the Phase 2 statement.** BUILT still says *"Tool exchanges are not message rows… Changing that means a schema change, which is Tier 3"*. Later work added readers of the trace, none of which feed the prompt: `receipts.for_trace` (response field), `journal.system_record_lines` (`program/reflection/journal.py:239-255`, journal only), `note_admin` (`:396-399`, review view), `corrections.reports_nothing_found` (`corrections.py:217`).
- Within one turn the tool messages **are** in the prompt (the loop appends them each iteration). The loss is across turns only.
- Severity: medium to high. It is the root of the "claims over a tool it cannot see" family (B25, the pending-claim false "done" at 6.7%).
- A fix is a design question: see 3.3.

## A8. Chunking. **CONFIRMED on all three counts** (two reproduced)

- **(a) A reply saved into an already-finalised conversation is never indexed. CONFIRMED, reproduced** (`/tmp/fp-repro2`, fake embedder):
  ```
  after close+finalise: chunks = 1, chunked = 1
  late user+assistant pair saved, then checkpoint_conversation (what chat.py's background task runs):
      chunks = 1   (2 messages never indexed)
      recovery queue (get_unchunked_ended_conversations) = []
  ```
  Mechanism: `finalise_conversation` marks `chunked` (`chunking.py:409`); `checkpoint_conversation` drops the open trailing group by design (`:369`), so it never writes the late pair; `get_unchunked_ended_conversations` lists only `chunked = 0` (`db.py:1264`) and **nothing in `program/` or `scripts/` calls it** (grep). `_resolve_conversation` checks `ended_at` once, at the start of the turn (`turn.py:182-189`), so a turn that resolved the conversation open before the sweep closed it keeps saving into the closed one.
  How reachable: the window is between `turn.py:492` (resolve) and `:495` (save the user message), plus the whole model call, against a sweep that snapshotted the conversation as idle. See (c).
- **(b) Chunk row and vector are separate writes, and a re-run skips a chunk that has no vector. CONFIRMED, reproduced.** `db.insert_chunk` commits the row (`chunking.py:299-311`); `store.upsert` follows (`:320`). If the upsert raises, the row stands. The re-run finds the row by `(conversation_id, chunk_index)`, the sha matches, and `result.chunks_skipped += 1; continue` (`:283-291`), **without upserting**, then marks the conversation chunked (`:409`). Reproduction: first `finalise` with `upsert` forced to raise, second `finalise` with it restored:
  ```
  chunk rows 1 | with a vector: 0 | conversation chunked = 1
  ```
  Retrievable by the lexical leg only, silently, forever. Only `scripts/reconcile_vectors.py` (manual) repairs it; nothing runs it.
- **(c) The idle sweep closes unconditionally after snapshotting. CONFIRMED.** `candidates = find_idle_conversations(now, …)` (`program/memory/idle.py:153`), then for each: `db.end_conversation(conversation_id)` (`:164`), which is `UPDATE conversations SET ended_at = ? WHERE id = ? AND ended_at IS NULL` (`db.py:536-541`). Nothing re-reads the last message time between the snapshot and the close, so a message that arrives in that interval is closed under. `exclude_conversation_id` protects only the conversation of the request that scheduled the sweep (`idle.py:134-137`), not the same person's turn on another request or the other person's.
- Severity: **high** (silent loss from memory is this project's worst class: raw experience that cannot be retrieved). Reachability is a narrow race for (a) and (c), an ordinary Chroma failure for (b).

## A9. Per-conversation serialization of turns. **CONFIRMED absent**

- The only per-conversation lock is `chunking._conversation_lock` (`program/memory/chunking.py:81-87`), and it guards chunking only. `grep -n "lock" program/engine/turn.py program/api/routes/chat.py program/engine/loop.py` finds no lock; `chat` is a sync `def` run in the threadpool (`routes/chat.py:128`), so a client retry (or two tabs) runs two `handle_user_message` calls in one conversation concurrently. ## Also noticed (nothing fixed)

1. `CLAUDE.md` ("State of this repo: Fresh build. No code exists yet… There are no build, test, lint, or run commands yet") and `NOW.md` ("Current state… No code written yet", "Last updated: [fill in…]") are stale against a tree with 1,986 tests. A session reading them is told something false.
2. `retrieval.search` passes the **raw user message** to `ollama.embed` (`retrieval.py:354`), and a chat message may be up to 50,000 characters (`chat.max_message_chars`) while `embed` rejects input past the model's context and does not truncate (`ollama.py:238-242`; the chunk budget is `embedding.max_input_chars`). So a long message probably degrades the vector leg on every such turn (a WARNING, `retrieval.py:356`). Unexercised.
3. B23's recovery is a private Chroma API; the chromadb pin in 4a is what keeps it from drifting silently.
4. Moving `ingest` off the event loop removes the accident that serialised uploads (A3), so 4a must carry the lock or B9 becomes live.
5. The kit tripwire (`kit-internal/bin/serve.py:36-41`) matches only the exact phrase `"retrieval failed"`, so other degraded states (`correction classifier could not run`, `could not be indexed`, `vector leg unavailable`) leave no marker.
6. `ollama.timeout_seconds` is live-editable while the classifier's is bootstrap-only *because* the grace derives from it (A12): the two were treated inconsistently.
7. `live_only` markers are evaluated at import (top of this file), so *collecting* tests during a measurement run touches Ollama.
